# 聊天并发整改与迁移

本说明面向护理双方聊天（`conversations`、`messages`），不替代容量压测报告。数据库迁移版本为 `20261002_mysql_0002`，承接冻结的 `20260905_mysql_0001`，要求 MySQL 8.4。不要改写发布基线或直接 `stamp head`。

## 数据规则

- 会话唯一键是 `SHA256(JSON(["care_chat", 排序后的参与者一, 参与者二, scope_type, scope_id]))`，JSON 使用紧凑分隔符和 ASCII 转义。空来源与 `profile` 都属于 `direct`，scope ID 为 `""`；`job`、`application`、`invitation` 分别保留自己的来源类型和 ID。排序只用于生成唯一键，不改变 `participant_a` 发起人含义。
- 同组历史会话按 `created_at, id` 选择最早的作为保留会话，消息和评价原 ID 保持不变，外键改指保留会话。删除的会话 ID 写入 `conversation_aliases`，供接口解析旧链接。审核记录等不受影响的业务表不做改写。
- 合并后同一评价人在同一会话会出现多条评价时，迁移在首次 DDL 前报错。未知来源类型、业务来源缺 ID、护理会话参与者缺失/相同也会报错。必须由业务负责人决定修正方式，并先保存合规的数据备份；迁移不会自动丢弃评价或猜测归属。
- 所有消息按合并后会话内的 `created_at, id` 回填从 1 开始的 `seq`。历史 `client_message_id` 保持 NULL。`last_seq` 是已提交消息的最大序号；`last_message_at` 是最后消息时间，没有消息时取会话创建时间。
- `(conversation_id, seq)` 和 `(conversation_id, sender_id, client_message_id)` 都有数据库唯一约束。不同历史消息允许使用 NULL 重试键；这不代表旧客户端自动获得幂等重试能力。

## 发布步骤

1. 在与生产版本和数据量接近的隔离 MySQL 副本演练，保存迁移耗时、磁盘增长、校验结果和恢复耗时。`TEST_MYSQL_URL` 只能指向可丢弃的测试库。部署进程使用的 `DATABASE_URL` 要由受控部署环境配置，不放入命令历史、报告或仓库。
2. 生成可恢复的数据库快照并验证恢复，记录当前 Alembic 版本及每张业务表行数。为合并准备会话 ID 映射、消息总数、评价总数的核对记录。备份与业务数据留在受控存储，不提交仓库。
3. 开启维护窗口，停止旧后端实例及相关写入任务，阻止聊天发送/建会话、招聘匹配产生会话、评价写入。必须等正在执行的事务结束，避免 preflight 与数据搬迁之间出现新写入。仅前端禁用发送按钮不足以保证停写。
4. 使用受控部署环境执行 `alembic -c alembic.mysql.ini upgrade head`。该迁移不支持离线 SQL 导出，因为必须检查实际数据和已完成的 schema 步骤。
5. 核验版本为 `20261002_mysql_0002`；消息数、评价数应保持不变；减少的会话数应由新增 alias 完整解释。检查每个会话 `COUNT(messages)=MAX(seq)=last_seq`（空会话为 0）、没有 NULL/重复序号，并确认消息及评价均无孤立引用。抽查有合并的会话和旧链接。
6. 部署后端后再发布前端。旧版只读接口保留兼容；新版聊天使用 `/api/v2/conversations` 游标列表和 `/api/v2/conversations/{id}/messages`。旧写入在兼容开关允许时仍走统一序号服务；待旧客户端退出后关闭兼容写入。不得把旧版本后端重新接到完成迁移的库继续写消息，因为它没有序号分配能力。
7. 完成鉴权、幂等重试、历史翻页、后台暂停轮询、Redis 断连回退等冒烟检查，通过 `/ready` 检查，再恢复写入。持续观察错误率、请求延迟、连接池等待和数据库锁等待。

## 资源与锁影响

这是维护窗口迁移，不宣称零停机。新增列、唯一索引和非空约束可能重建表或持有元数据锁；长事务会阻塞 DDL。回填临时表使用 InnoDB，并为每条消息存放 ID 与序号，排序、索引构建、undo/redo 和临时空间均需预留余量。消息总量越大，排序和批量 UPDATE 时间越长。会话与评价的合并计划在迁移进程内存中计算，大库应先在副本验证内存上限。

不要在迁移期间调整为读副本获取 `last_seq`。发送的序号递增、消息插入和会话时间更新在同一个短事务中提交，行锁只串行化同一会话。缓存只储存某个已提交 `last_seq` 对应的完整最新页，不能代替数据库；历史页和增量同步走序号范围查询。

## 接口与运行参数

- `GET /api/v2/conversations`：会话按最近消息时间与 ID 排序，使用 `cursor` 获取下一页，返回 `items`、`next_cursor`、`has_more`。身份来自认证信息，不接受用户用查询参数指定其他人的列表。
- `GET /api/v2/conversations/{id}/messages`：默认每页 50 条，上限 100；不传游标取完整最新页，`before` 取更早历史，`after` 增量同步，两个参数不能同时传。消息按 `seq` 升序返回；响应包含 `items`、`older_cursor`、`sync_cursor`、`has_more`。初始/历史页的 `has_more` 表示还有更早历史，增量页表示还有未同步的新消息。游标有签名并绑定会话，不能挪给其他会话使用。
- `POST /api/v2/conversations/{id}/messages`：必须提供 UUID `client_message_id`；新消息返回 201，同一发送人以相同键和相同正文/附件重试返回原消息及 200，相同键携带不同内容返回 409。发送人从认证身份确定。前端一次发送意图只生成一次键，失败重试继续用原键。
- 发送回执只合并该消息，不推进增量同步游标。历史加载也不推进同步游标；增量轮询根据实际取到的末条消息推进，并在 `has_more` 为真时继续补齐。页面隐藏、切换会话或退出登录后取消相应请求；遇到 429 按 `Retry-After` 退避。

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `CARE_CHAT_LEGACY_SEND_ENABLED` | `true` | 兼容 v1 发送；旧客户端退出后设为 `false` |
| `CARE_CHAT_CACHE_ENABLED` | `true` | 启用 Redis 完整最新页缓存 |
| `CARE_CHAT_READ_CONCURRENCY` | `8` | 每进程最多同时执行的消息页数据库读取数 |
| `CARE_CHAT_SEND_CONCURRENCY` | `8` | 每进程最多同时执行的发送操作数 |
| `CARE_CHAT_SEND_RATE` | `5` | 每账号每秒补充的发送令牌数 |
| `CARE_CHAT_SEND_BURST` | `10` | 每账号可积累的突发发送令牌数 |

Redis 共享账号令牌桶，最新页缓存 TTL 为 30 秒；Redis 操作使用 100 毫秒连接/读超时，失败后熔断 10 秒。Redis 不可用时缓存读回退到数据库、发送账号限流回退到当前进程令牌桶，消息仍由数据库持久化。**降级后的账号速率和突发上限可能随 worker/实例数倍增**，本地并发读取/发送上限也按进程数累加；它们不能代替部署层的总并发/总流量控制。增加 worker 前必须把总数据库连接数、读写闸门和 MySQL 实测吞吐一起核算。部署层继续保留全局/IP 限流，避免故障期间把所有请求无界压给数据库。

生产 Compose 已透传上述变量。随仓库提供的 Nginx 对 v1/v2 会话接口按入口 IP 限制为每秒 30 次、突发 60 次；这是入口保护默认值，医院共享出口及多层代理部署应根据实际拓扑调整，不能当作账号额度或容量承诺。

## 失败与恢复

MySQL DDL 会隐式提交，不能把 `upgrade` 失败理解为整个迁移已回滚。本迁移按已存在的列、表及索引跳过成功步骤，支持在**持续停写**且数据库结构没有被手工改坏时重新执行。消息/评价搬迁、alias 写入、序号和水位回填之间不插入会隐式提交的普通 DDL，数据操作失败时由连接回滚；成功的数据搬迁在随后建约束的 DDL 时提交。

- preflight 数据错误：尚未新增字段；保持停写，明确修复数据并留存处置记录后重新执行。
- 新增列、表或索引阶段失败：记录错误和实际 schema，先排除磁盘、锁等待或权限问题；保持停写，重新执行同一迁移。重跑会重新校验冲突、重算相同排序并补齐缺失约束。
- 数据搬迁已成功、最后索引或版本写入失败：不要手动删除 alias、倒回外键或直接修改 Alembic 版本。保持停写后重跑；版本和全部约束校验成功才允许部署流量。
- 出现意外结构、身份歧义、恢复期间已发生写入，或不能确认一致性：停止重试，将完整数据库恢复至维护前已验证的快照，再恢复原版本应用。不能只恢复单张消息表或只回滚应用代码。

`downgrade` 明确拒绝自动执行，因为合并会话无法无损推断拆分。需要回退时必须同时恢复维护前数据库与兼容的应用版本。

## 验收与容量声明

默认测试包含身份归一、合并和冲突预检测试；隔离 MySQL 测试验证实际索引、唯一约束、历史搬迁与排序 SQL。并发写入必须在真实 MySQL 中验证，SQLite 测试不能证明 MySQL 行锁行为。

上线前在固定实例规格、进程数、连接池、数据量下记录实际吞吐、P95/P99、错误率与锁等待。必须覆盖相同重试键并发仅产生一条消息、同一会话高并发保持连续序号、多会话并行、千条历史翻页/同步无遗漏、Redis 故障后发送仍可提交、无权限用户命中缓存仍被拒绝。只有保留这些实测记录后，才能给出可承载的并发量；代码整改完成不等于已证明某个容量数字。
