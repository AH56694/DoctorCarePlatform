# 生产部署与运维手册

本手册描述单机容器应用连接私有 MySQL 8.4、Redis 的部署基线。开始生产发布前，必须关闭《企业级审计与整改报告》中的上线阻断事项。这里提供了配置和步骤，本轮没有在真实生产环境执行部署。

## 环境准备

- 使用 `docker-compose.production.yml`；开发用的 `docker-compose.yml` 不承担生产配置。
- 为数据库预建库和独立账号：业务账号只拥有所需表的数据操作权限，AI 服务账号只拥有所需兼容表权限，迁移账号单独拥有建表、索引和视图权限。应用不使用 root。
- MySQL、Redis、对象存储仅允许批准的应用网络访问。部署示例没有开放这些服务的宿主端口；远程连接的传输保护需要按实际基础设施配置和验证。
- 准备经校验的本地 Embedding 模型目录，挂载到 AI 服务的 `/app/models/embedding`。模型目录为空、不可读或无法加载时，就绪检查不会通过。
- 复制 `.env.production.example` 为忽略版本控制的 `.env.production`，替换全部占位符。数据库 URL 中密码的特殊字符必须 URL 编码；`MYSQL_PASSWORD` 使用原始密码。
- `AUTH_SECRET_KEY` 与 `RAG_SERVICE_TOKEN` 使用不同的至少 32 字符随机秘密。CORS 使用明确的 HTTPS 来源 JSON 数组。生产默认秘密和宽泛 CORS 会被启动校验拒绝。
- 此配置假设 HTTPS 在宿主反向代理或负载均衡器终止，然后代理到 `127.0.0.1:8080`。配置有效证书、HTTPS 跳转与适当的 HSTS。入口若转发真实客户端 IP，必须只信任明确的代理地址；不能无条件信任外部 X-Forwarded-For。

## 新数据库的发布步骤

```powershell
docker compose --env-file .env.production -f docker-compose.production.yml config --quiet
docker compose --env-file .env.production -f docker-compose.production.yml build
docker compose --env-file .env.production -f docker-compose.production.yml --profile migration run --rm migrate
docker compose --env-file .env.production -f docker-compose.production.yml up -d
docker compose --env-file .env.production -f docker-compose.production.yml ps
```

迁移命令必须成功后才启动新版本。就绪探针会校验业务库的迁移版本；版本不匹配时后端不会被标记为就绪。

创建首个管理员时交互输入密码，避免把密码放进命令行历史：

```powershell
docker compose --env-file .env.production -f docker-compose.production.yml exec backend python scripts/create-admin.py --phone YOUR_ADMIN_PHONE
```

该命令要求至少 12 字符密码，拒绝直接提升已有账号权限，并记录创建审计。管理员角色不是普通注册可选项。

## 已有数据库首次接入迁移管理

历史 PostgreSQL 迁移链不能在 MySQL 执行。MySQL 基线检测到已有业务表会主动停止，避免把“存在同名表”误当作“结构正确”。

1. 在不影响写入一致性的条件下备份，并在隔离环境恢复验证。
2. 将现有表、列类型、空值规则、索引、唯一约束、外键、字符集和视图与 `migrations/mysql_versions/20260905_baseline.sql` 比对。
3. 检查历史重复应聘/邀请、无归属问诊、错误认证状态及孤立数据。对实际差异编写专项迁移，在恢复副本执行并验收。
4. 只有在确认实际结构与目标基线一致后，才由数据库负责人将已确认的精确版本纳入 Alembic 管理。不要直接执行 `stamp head` 跳过检查。
5. 后续迁移只追加版本，不修改已发布基线。MySQL DDL 不保证整体事务回滚，失败后需检查已经执行的步骤。

## 健康、日志与容量

- `/health`：进程存活，不证明模型、数据库和业务已就绪。
- 后端 `/ready`：数据库连接、生产 Redis 和 MySQL 迁移版本。
- AI `/ready`：需 `X-Service-Token`，检查模型初始化。探针不证明远程 LLM 的医学效果或所有外部依赖可用。
- 响应中的 `X-Request-ID` 用于定位后端请求日志。请求日志保留路由模板、状态码与耗时，禁止补回病历正文、令牌或证件信息。
- 监控至少包含 HTTP 5xx、429、超时、就绪失败、数据库连接池、模型初始化失败、任务失败与磁盘空间。阈值应由压测和运营目标确定。
- 示例资源配额是起点，需实际验证。当前 FAISS 和内存 Agent 状态按单实例部署；不要直接增加 AI worker 数或副本数。
- 当前知识入库仍有进程内后台任务，进程退出可能留下 pending 状态；上线前需改为可恢复的持久化任务。短信接口当前明确报告未实现，不可作为真实通知成功依据。

## 发布验收

必须记录：登录与失效、各角色的越权拒绝、患者发布招聘、护理应聘与邀请、接受匹配、聊天与评价、本人问诊历史、流式成功与超时、知识入库及失败恢复、身份核验及证据审计。

还需验证：两个独立浏览器账号之间不能访问对方病历；反向代理不缓冲 SSE；慢模型不拖垮普通业务；大量登录尝试返回 429；内部 AI API 缺少服务令牌返回 401；错误配置不能启动生产应用。

CI 配置包括前端构建/测试/依赖审计、后端与 AI 单元测试、MySQL 实际迁移与约束检查。文件落库后还需要在代码托管平台运行 CI，并把对应检查设为受保护分支的合并条件。

## 备份与恢复

数据库、向量索引、对象文件和密钥版本需要协调备份，备份应加密并保存在受控的独立位置。根据业务目标约定恢复点和恢复时间；仅有“备份成功”日志不能证明可以恢复。

每次涉及数据库的发布前都要验证恢复路径。回滚应用镜像必须确认旧程序仍兼容当前表结构；破坏性变更采用先扩展、再切换、后清理的方式。本次基线禁止自动降级删除整库，恢复依靠经验证的备份流程。

## 开发环境升级

新依赖已在本项目虚拟环境验证。其他开发机器需重新安装 `requirements.txt`、`python-service/requirements.txt` 和 `requirements-dev.txt`，前端执行 `npm ci`。生产容器只安装带哈希的部署锁文件。Windows 本地开发与 Linux 部署的原生包不同，不应直接混用操作系统专用锁文件。

本次会清除旧版浏览器持久化会话，需要重新登录。未填写新的证件号时前端省略该字段，避免保存普通资料时意外清空证件并撤销认证；明确提交空证件号仍会触发重新核验。
