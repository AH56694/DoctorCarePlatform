# 企业级审计与整改报告

审计日期：2026-09-05。范围：业务后端、AI 服务、前端请求与会话、数据库模型及迁移、容器配置、依赖和测试。

## 结论

项目具备原型业务闭环，但原始状态不满足真实患者数据的生产上线条件。本轮已完成一批可验证的安全与工程基础改造，适合继续在隔离测试环境联调。生产配置文件和测试通过不等于医学有效性、合规审查、容量及恢复能力已经验收。

建议保留现有单仓库与两个服务的结构，先补齐数据保护、真实业务接入和质量门禁，再根据压测结果决定拆分服务或扩容，避免以增加组件数量代替工程质量。

## 仍然阻断真实业务上线的事项

1. **敏感数据保护。** `id_number`、`basic_info`、问诊与消息正文仍以明文业务字段存储；字段名带 encrypted 不能证明存在完整加密链路。需要按数据分类实现密钥管理、加密/解密授权、密钥轮换、备份加密、保留及删除策略，并审计管理员读取敏感信息的行为。
2. **身份与通知的真实接入。** 注册尚未验证手机号归属，短信供应商适配器尚未实现；新增人工身份核验入口需要外部核验依据和运营流程。已有自动“认证成功”的历史数据必须重新核查，不能仅依赖代码更新。
3. **附件链路。** MinIO 仍是预留能力，部分前端上传只是演示数据处理。需要实现私有对象存储、短时授权、类型和内容校验、扫描、保留周期及审计；未经验收的上传入口不得承载真实证件和病历。
4. **医疗业务验收。** 现有知识检索单元测试不等于医疗效果评测。需要临床专业人员评审知识来源、更新版本、危险症状处理、依据不足时的行为、人工升级和用户告知，并完成适用地区的产品与合规评估。
5. **环境与运维验收。** 必须在隔离 MySQL 8.4 和真实部署镜像上执行 CI、迁移、权限矩阵、完整业务链路、压测、故障与备份恢复演练。HTTPS 入口、内网访问、日志告警、访问权限和密钥管理尚需在实际基础设施上配置。

## 设计依据

- 同步阻塞调用的处理方式依据 [FastAPI 并发说明](https://fastapi.tiangolo.com/async/)。本轮只转换不含异步调用的处理器，混合流程仍需继续拆分短事务。
- 就绪依赖与启动顺序依据 [Docker Compose 启动顺序文档](https://docs.docker.com/compose/how-tos/startup-order/)。容器启动不等同于应用已经能处理业务。
- 接口访问控制、令牌验证、限流和错误处理参考 [OWASP REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)。这些是工程对照依据，不是已经通过第三方认证的声明。
